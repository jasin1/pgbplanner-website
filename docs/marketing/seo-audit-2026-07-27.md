## 2. Open Graph / Twitter card coverage per route

`BaseLayout.astro:34-53` unconditionally renders a full OG set (`og:type`, `og:site_name`, `og:locale`, `og:title`, `og:description`, `og:url`, `og:image` + width/height/alt) and a Twitter `summary_large_image` card for **every** route — so no route is silently missing OG tags. The `og:title` / `og:description` values correctly mirror whatever `title`/`description` the page passed in (or the defaults, see Finding 1-3 above).

**Finding 5 — No route ever overrides `ogImage`.** Every single page — homepage, `/privacy`, `/vragenlijst`, all `/blog/[slug]` posts, etc. — falls through to the same default `/og.jpg` (`src/layouts/BaseLayout.astro:9`). A shared link to a blog article, the privacy page, and the homepage all render an identical social-preview image. Files: `src/layouts/BaseLayout.astro` (prop exists but unused elsewhere), every file under `src/pages/`. Effort: **M** (needs per-page/per-post image assets + wiring `ogImage={...}` through the pages/blog frontmatter that should have one).

**Finding 6 — `og:image:alt` is a hardcoded generic string** ("PGB Planner – Voorbeeldafbeelding bij gedeelde link", `BaseLayout.astro:44-47`) for every route, not descriptive of the actual page/article. Effort: **S** (would need an `ogImageAlt` prop added to `BaseLayout.astro`).

**Finding 7 — `og:type` is hardcoded to `"website"` for all routes** (`BaseLayout.astro:35`), including blog articles, which should ideally emit `og:type="article"` with `article:published_time`. No prop exists to override it. Effort: **S** (add an `ogType` prop to `BaseLayout.astro` and pass it from `blog/[...slug].astro`).

## 5. Per-article metadata support in `BaseLayout.astro`

`BaseLayout.astro` accepts exactly four props: `title`, `description`, `ogImage`, `hideHeader` (`src/layouts/BaseLayout.astro:6-11`). It does **not** accept a canonical override or an OG type override.

What already works correctly for blog articles:
- **Title/description**: `blog/[...slug].astro:22` passes `` `${post.data.title} • PGB Planner` `` and `post.data.description` straight from the content-collection frontmatter into `BaseLayout`. This is unique per post and correctly wired — no gap here.
- **Canonical**: computed independently of any prop, from `Astro.url.pathname` (`BaseLayout.astro:15-16`), so each blog post automatically gets its own correct canonical URL. No gap here either.

What is missing:
- **Per-article OG image**: the blog content-collection schema (`src/content/config.ts:5-11`) has no `image`/`ogImage`/`heroImage` field at all (only `title`, `description`, `pubDate`, `draft`, `heroAlt` — note `heroAlt` exists with no corresponding `heroSrc`/`heroImage` field to be the alt text *for*). `blog/[...slug].astro:22` never passes an `ogImage` prop to `BaseLayout`, so every article silently falls back to the site default `/og.jpg` (same as Finding 5).
- **Per-article OG type**: no `ogType` prop exists on `BaseLayout` (Finding 7), so articles emit `og:type="website"` instead of `article`.

**Finding 10 — Blog articles fall back to site-default OG image and `og:type`, not because `BaseLayout` can't take the data, but because (a) the content schema doesn't collect it and (b) the page doesn't forward it.** The minimal change to close this (not implementing, per instructions) would be: add an optional `image: z.string().optional()` field to the blog schema in `src/content/config.ts`, and in `blog/[...slug].astro` pass `ogImage={post.data.image}` (with a fallback to the current default when absent) and a new `ogType="article"` prop through to `BaseLayout.astro`. Effort: **M** (schema change + two files + at least one real image asset per future post).

## 6. Canonical URL handling (www vs non-www, absolute vs relative)

- Canonicals are **always absolute**: `BaseLayout.astro:13-16` builds `canonical` from `Astro.site` (a full URL from `astro.config.mjs`) concatenated with `Astro.url.pathname`. No relative canonicals exist anywhere. Good.
- **`astro.config.mjs:6` sets `site: 'https://www.pgbplanner.nl'`** (www subdomain). This is the fallback host baked into every canonical tag and into the sitemap integration's URL generation.
- **`public/robots.txt`** also points to the www host (`Sitemap: https://www.pgbplanner.nl/sitemap-index.xml`) — internally consistent with `astro.config.mjs`.
- However, **CLAUDE.md's own project header states the live URL is `https://pgbplanner.nl`** (apex, no www) — a direct mismatch with what the code and config assume.
- **Finding 11 — Inconsistent host across the codebase for the same "privacy" destination.** Three different URLs are used in three different places for what is nominally the same page: `Footer.astro:42` links to `https://app.pgbplanner.nl/privacy` (app subdomain); `privacy.astro:206` self-references `https://pgbplanner.nl/privacy` (apex, in the page's own body copy, "meest recente versie is altijd te vinden op..."); and `astro.config.mjs`/`robots.txt` both assume `https://www.pgbplanner.nl` (www) as the canonical host for this exact page. There is a fully-built `/privacy` page in this repo (`src/pages/privacy.astro`), yet the site's own footer sends users to a *different* domain (`app.pgbplanner.nl/privacy`) instead of linking to it. Whether that's intentional (single source of truth lives in the app repo) or a leftover bug needs a product decision — the audit only confirms the three-way inconsistency exists in code. Effort: **M** (requires confirming which host/URL is canonical, then a one-line fix in whichever files are wrong).
- No `netlify.toml` and no `_redirects` file exist in the repo (confirmed via filesystem search), so there is no code-level enforcement of a single canonical host (e.g., apex → www or www → apex 301). Any such redirect must currently live in Netlify's dashboard config, outside this repo, and could not be verified here. Effort to confirm: **S** (check Netlify site settings); effort to fix in-repo if needed: **S** (add `_redirects` or `netlify.toml`).
- Trailing-slash consistency is not pinned (`astro.config.mjs` sets no `trailingSlash` option, so Astro defaults to `'ignore'`). Blog links are generated with a trailing slash (`` `/blog/${post.slug}/` ``, `blog/index.astro:25`), but nothing prevents the same content being reached without one, in which case the canonical tag (built from the literal request path) would emit a different URL for the same page depending on how it was reached. Effort: **XS** (set `trailingSlash: 'always'` or `'never'` in `astro.config.mjs`) — flagging only, not proposing the change per instructions.
